# びじゅありん 引き継ぎメモ（2026/08/21時点）

## 1. びじゅありんの目的

家事や日用品の在庫は「見えない・忘れる・気づいたら切れている」という問題が起きやすい。びじゅありんは、家事タスクと消耗品（日用品）の状態を**一覧で可視化**し、

- 何をやっていて、何をやっていないか
- 何が家にあって、何が少なくなっているか

を常に把握できるようにすることで、家事・買い物の抜け漏れを防ぐことを目的とした個人向けアプリ。AIとの連携により、大まかな家事名からの具体的なタスク分解や、季節に応じた家事提案、消耗品の購入タイミング予測も行う。

**重要な設計思想（今回のセッションで明確化）**：
タスク・消耗品はいずれも「完了/購入したら消えるTODOリスト」ではない。**登録したものは常に一覧に残り続け**、優先度の高いもの（消耗品ならアラート中のもの、タスクなら次回予定日が近い・過ぎているもの）が**上に表示される**ことで、全体を俯瞰できることが本質的な価値である。

## 2. びじゅありんの概要

### 技術構成
- **バックエンド**：FastAPI + SQLAlchemy + SQLite。JWT認証（`python-jose`）、パスワードハッシュ化（`passlib`/bcrypt）。AI連携はGoogle Gemini API（`gemini-2.5-flash`）。
- **フロントエンド**：React + Vite + React Router。スタイルはプロトタイプの`style.css`をそのまま流用（ヴィンテージ・手帳風のデザイントーン）。カスタムフォント「木漏れ日ゴシック」を使用。
- **リポジトリ構成**：モノリポ（`backend/`, `frontend/`, `frontend_designs/`（プロトタイプ）, `docs/`）。Gitフローは機能ごとにブランチを切ってPRでmainにマージする方式。バックエンドは`feature/backend-init`からmainにマージ済み。フロントエンドは`feature/frontend`ブランチで作業中（まだmainに未マージ）。

### バックエンドのAPI構成（実装済み）
- **認証系**（`/api/auth`）：`register`, `login`, `logout`, `password-reset`（今回のセッションで追加。メール送信なしの簡易版）
- **タスク管理**（`/api/tasks`）：一覧取得、新規登録、更新、削除、完了（`/complete`で次回予定日を自動再計算）
- **消耗品管理**（`/api/items`）：一覧取得、新規登録、更新、削除、使用（`/consume`）、購入完了（`/restock`）
- **AI連携**（`/api/ai`）：`breakdown`（家事の細分化）、`propose`（季節・住環境からの提案）、`predict`（消耗品の購入タイミング予測）

### データモデルの要点
- `Task`：`title`, `description`, `frequency_days`（繰り返し日数）, `next_due_date`（次回予定日）, `category`（自由入力の文字列）, `is_completed`
- `Item`：`name`, `current_stock`（残量）, `alert_threshold`（アラート基準値）, `purchase_cycle`（購入サイクル日数）, `category`（自由入力の文字列）, `is_alert`（プロパティ、DBには保存されない計算値）
- カテゴリは**当初は固定の選択肢（水回り/キッチン/お風呂/トイレ等）だったが、今回のセッションで自由入力方式に変更**（詳細は後述）

## 3. 今までのステップとその内容

### フェーズ0：バックエンド実装（前セッション以前）
- FastAPIで認証・タスク・消耗品・AI連携の4系統を実装、`feature/backend-init`ブランチからmainにマージ済み
- Swagger UIで動作確認済み

### フェーズ1：フロントエンド技術選定・環境構築
- 技術選定を相談し、**React + Vite + React Router**を採用（学習目的も兼ねる）
- ビルドツール：Vite、ルーティング：React Router、スタイリング：既存`style.css`を流用、と決定
- Viteプロジェクト作成（`npm create vite@latest frontend -- --template react`）、ESLintを選択
- `react-router-dom`をインストール
- 不要なデフォルトファイル（`App.css`, `assets/`）を削除し、`style.css`を`frontend_designs/`からコピー
- カスタムフォント「木漏れ日ゴシック」を配布元（フリーフォントのMODI工場）からダウンロードし`src/fonts/`に配置、CSSのパスを修正

### フェーズ2：ルーティングとページ骨組み
- 12画面分のルート設計（`/login`, `/home`, `/tasks/:taskId`など）を`App.jsx`に実装
- 12ページ分の空コンポーネント（プレースホルダー）を作成し、ルーティングの疎通を確認

### フェーズ3：共通基盤の構築
- **`Header.jsx`**：戻る/編集リンクを持つ共通ヘッダー（props: `title`, `backTo`, `backLabel`, `actionTo`, `actionLabel`, `variant`）
- **`api/client.js`**：`fetch`の共通処理。JWTトークンの保存（`localStorage`）・自動付与、エラーハンドリング（`detail`メッセージの抽出）。`apiGet`/`apiPost`/`apiPut`/`apiDelete`のショートカット関数
- バックエンドに**CORS設定**（`CORSMiddleware`、`http://localhost:5173`を許可）を追加

### フェーズ4：認証系4画面の実装
- **ログイン画面**：`apiPost('/api/auth/login')` → トークン保存 → `/home`へ遷移。実際にバックエンドと接続して動作確認済み
- **新規登録画面**：`apiPost('/api/auth/register')`。パスワード確認はフロント側のみでチェック
- **登録完了画面**：静的な表示のみ
- **パスワードリセット画面**：バックエンドに元々このエンドポイントが存在しなかったため、設計から追加した
  - API設計書を確認し、パスワードリセットAPIが未定義であることを確認
  - **案A（メール送信なしの簡易版）**を採用：メールアドレス＋新パスワードを直接送信して更新する方式。個人利用規模のため許容
  - バックエンドに`PasswordResetRequest`/`PasswordResetResponse`スキーマと`POST /api/auth/password-reset`エンドポイントを追加
  - フロント側フォームも実装し、動作確認済み

### フェーズ5：共通UI部品の改善
- **`window.alert`/`window.confirm`をReact製に置き換え**（OSネイティブのダイアログはUXが悪く、開発者からの明確な要望があったため）
  - **`ToastContext.jsx`**：`showToast(message)`で呼べる、自動で消えるトースト通知。Context + Providerパターン
  - **`ConfirmContext.jsx`**：`await showConfirm(message)`で呼べる、Promiseベースの確認モーダル。`true`/`false`で結果を返す。オーバーレイ表示で他の操作をブロックしない設計
  - `main.jsx`に両Providerを追加（`ToastProvider` → `ConfirmProvider` → `App`の順にネスト）

### フェーズ6：ホーム画面の設計・実装
- **表示方式の決定**：プロトタイプ通り「フローティングパネル方式」を維持（別ページ遷移ではなく、ホーム画面上にドラッグ可能なパネルが重なる形式）
- **パネル管理方式の決定**：カードごとに個別パネルではなく、**共通パネル1つを使い回す**方式（`openPanel`ステートで種類を管理、`selectedTask`/`selectedItem`で対象データを管理）
- **`FloatingPanel.jsx`**：汎用の汎用ドラッグ可能パネルコンポーネント。`isOpen`が`false`のとき`return null`でアンマウントする設計
- **設計方針の見直し**：当初`Home.jsx`にすべてのロジックを書いていたが、開発者から「Home.jsxに機能が集約しすぎ」と指摘があり、**各パネルを`components/panels/`配下の独立コンポーネントに分離**する設計に変更。フォームの入力値管理は各パネル自身が持ち、API通信・データ再取得は`Home.jsx`側が担当する役割分担とした
- 実装したパネル（すべて`src/components/panels/`）：
  - `TaskRegisterPanel.jsx` / `TaskDetailPanel.jsx` / `TaskEditPanel.jsx`
  - `ItemRegisterPanel.jsx` / `ItemDetailPanel.jsx` / `ItemEditPanel.jsx`
- `Home.jsx`本体：タスク・消耗品の一覧取得（`useEffect`＋`Promise.all`）、各種ハンドラー関数（作成・更新・削除・完了・使用・購入完了）、パネルの開閉制御

### フェーズ7：消耗品タブの仕様拡張
開発者より「消耗品一覧は全件を把握できることが本質。アラート中のものだけでなく全部を表示し、優先度の高いものを上に出すべき」という指摘があり、以下を実装：
- 表示ロジックを「アラート中のみフィルタ」→「**全件表示、アラート中を上にソート**」に変更
- **カテゴリの自由入力化**：固定の`<select>`から、`<input> + <datalist>`（候補表示付き自由入力）に変更。過去に使ったカテゴリ名が入力候補として出る
- **カテゴリ絞り込みドロップダウン**：ホーム画面の消耗品一覧に「すべて/カテゴリ名」の絞り込みセレクトボックスを追加
- **インライン操作**：一覧のカードから直接「➖ 1つ使う」ボタンを押せるようにした（従来は詳細パネルを開く必要があった）
- **0件時の案内表示**：消耗品・タスクともに、登録が0件の場合や絞り込み結果が0件の場合の案内文を追加

### フェーズ8：タスクタブの仕様拡張
消耗品と同じ考え方をタスクにも適用：
- **「完了する」ボタンの機能実装**：`POST /api/tasks/{id}/complete`を呼び、次回予定日を更新
- **並び替えロジック**：`next_due_date`（次回予定日）が近い、または未設定のものを上に表示するソートを追加
- **カテゴリの自由入力化**：消耗品と同じ`datalist`方式をタスクにも適用

**保留事項として明確化**：タスクの繰り返し間隔について、「ゴミ出しは火曜・金曜のように複数曜日で定められる場合がある」という要件が出た。これは現状の`frequency_days`（単純な日数）では表現できず、バックエンドのモデル・スキーマ変更（繰り返しタイプ・曜日カラムの追加など）が必要。**混乱を避けるため、一通りソフトが完成した後のアップデート課題として保留**することで合意している。

### フェーズ9：AI連携機能の実装
- プロトタイプでは`10_ai_integration.html`という独立ページでAI機能を提供する想定だったが、**開発者の意向によりホーム画面のAIチャット1つに機能を集約**する方針に変更（`AiIntegration.jsx`ページは現在未使用）
- **`breakdown`（家事の細分化）**：チャット欄に大まかな家事名を入力すると、AIが提案するサブタスク一覧がチャット吹き出し内にカード形式で表示される。各サブタスクに「タスクに登録」ボタンがあり、押すと**`TaskRegisterPanel`が初期値（タイトル・推奨頻度）付きで開く**（確認・微調整してから登録する方式を採用）。この対応のため`TaskRegisterPanel`に`initialValues`propsを追加した
- **`predict`（購入時期予測）**：`ItemDetailPanel`に「🔮 購入時期をAIに予測してもらう」ボタンを追加。押すと`POST /api/ai/predict`を呼び、AIのアドバイス文をパネル内に表示する。消費・購入履歴が2件以上ないとバックエンド側で400エラーになる仕様
- **`propose`（季節提案）**：チャット入力欄の上に「🍃 季節の家事を提案してもらう」ボタンを追加。押すと季節・住環境を選ぶ簡易フォームがチャット欄に表示され、送信すると`breakdown`と同じ表示形式（サブタスクカード＋タスク登録ボタン）で提案結果が表示される

2. **未使用ページの整理**：`AiIntegration.jsx`（`/ai`ルート）はAI機能をホームに統合したため使われていない。削除するか、別の用途に転用するか要検討
3. **`requirements.txt`の整備**：バックエンドの依存パッケージが固定されていない（引き継ぎメモ当初からの課題）
4. **`consume`/`restock`のクエリパラメータ方式**：バックエンドが`quantity`/`restock_quantity`をクエリパラメータで受け取る設計になっており、将来的にリクエストボディ方式に統一するかは要検討（現状は動作に支障なし）
5. **GitのPull Request作成**：`feature/frontend`ブランチはこまめにコミット・プッシュされているが、まだ`main`にマージされていない

## 6. 開発の進め方に関する留意点（次セッションへの申し送り）

- 開発者はコードを手打ちで実装しており、**タイポによるバグが頻発**する（変数名の綴り間違い、`export default`の書き忘れ、クォートの種類の誤りなど）。エラーが起きた際は、まずブラウザの開発者ツール（F12→Console）のエラーメッセージを確認する手順を徹底すると原因特定が早い
- ブラウザが「直したはずなのに反映されない」場合、キャッシュの影響のことがあるため、**強制リロード（Ctrl+Shift+R）**を試すと解決することがある
- 開発者は「一覧で全体を把握できること」を強く重視する設計思想を持っている。新機能を提案する際はこの軸に沿っているか意識するとよい
- Gitのコミットはこまめに行う運用（機能単位で区切って都度コミット・プッシュ）。開発者自身が単独でコミットを進めることもあるため、作業再開時は`git log --oneline`で最新のコミット履歴を確認してから進めるとよい
